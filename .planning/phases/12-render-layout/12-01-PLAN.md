## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| WASM (ketcher) → store → DOM | The `inchiKey` is computed in-browser by the trusted Ketcher WASM worker and stored verbatim. No network, no backend, no user-typed free text reaches this strip. |
| App → clipboard | The copy button writes the in-app computed key to the system clipboard via the Clipboard API. |

## STRIDE Threat Register

This phase is pure client-side rendering of a trusted, locally-computed 27-char string. The realistic threat surface is minimal; threats below honestly reflect that.

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-01 | Tampering (XSS) | InchiKeySection span rendering | accept | Segments render as React text children via `{inchiKey.slice(...)}` — React escapes text nodes by default. No `dangerouslySetInnerHTML`, no `innerHTML`, no `eval`. Input is the WASM-computed key, not untrusted free text. No mitigation needed beyond React's default escaping. |
| T-12-02 | Information disclosure | Clipboard write | accept | `navigator.clipboard.writeText` writes only the already-displayed public InChIKey (no secrets/PII). Equal to the existing InChI copy button. |
| T-12-03 | Denial of service | parseInchiKey on malformed key | accept | parseInchiKey never throws and returns `[]` for any non-27-char input (Phase 11 contract / T-11-01) → strip falls through to the placeholder. No crash path. |
| T-12-SC | Tampering | npm/pip/cargo installs | n/a | Zero new dependencies introduced this phase (confirmed by CONTEXT.md / STATE.md). No install tasks → no package-legitimacy checkpoint required. |
</threat_model>
